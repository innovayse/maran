# Security Rules

Normative. Security is the product's core promise — every PR is reviewed against this checklist and any "no" blocks merge.

## The checklist (reviewer runs it verbatim)

1. **Input:** every external input (HTTP body/query/route, reseller API (`/api/v1/reseller-api/`), agent rpc) validated at the boundary — FluentValidator on the C# request, revalidation in the agent. No value reaches a template, path, or SQL untouched.
2. **Paths:** anything path-like is contained by a descriptor walk, not by a string check. Every
   write goes through `ops::files::open_parent_directory`, which descends with `openat` and
   `O_NOFOLLOW`, checking ownership at each component, inside `fork_as_account` — so a component
   swapped for a symlink between the check and the use is refused rather than followed.
   `resolve_in_home` canonicalizes and confirms containment in `/home/<account>/`, but it is a
   *locating* aid used by two read paths, and it contains nothing that is written: an earlier
   version of this rule named it as the containment, which is wrong and was worth correcting,
   because a reviewer who believes a string check is the control stops looking for the descriptor
   one. Never trust an extension, never trust a `..`-free-looking string, and never decide
   anything about a path by parsing its text — a customer's symlink in their own home once made
   root create `/etc/ld.so.preload`, and the fix was to anchor on descriptors and move the target
   out of any directory a customer owns.
3. **Shell:** no shell strings anywhere, no string-built commands. Agent spawns processes with argv arrays only, allow-listed binaries, no `sh -c`. The API spawns nothing at all.
4. **Config-file injection:** any caller-supplied value written into a line-oriented or
   structured config file — a crontab entry, an nginx directive, an env file, a systemd unit —
   MUST reject newlines, carriage returns and control characters before it is written. This is the
   panel's equivalent of SQL injection: one embedded newline turns a single entry into several,
   which is how a customer escalates from "my own cron job" to "an extra job, a MAILTO, a PATH".
   Rendering through a template does not make it safe; the value is validated, not escaped.
5. **SQL:** EF Core parameterized only; approved `// raw-sql:` comments are parameterized too. String-concatenated SQL is an automatic reject + incident.
6. **AuthZ:** every endpoint declares its permission; every tenant query is account-scoped via the
   global filters. This is no longer a thing a reviewer remembers: `TenantScopeTests` walks every
   module's EF model and fails when an entity that is a customer's row has no query filter, so a new
   tenant table — ours or a third party's — is covered without anyone extending a list. "A customer's
   row" is not "spells it `AccountId`": the census follows REQUIRED relationships transitively, so an
   entity scoped through its parent and carrying no account id of its own — `SiteHostname`, filtered
   through `hostname.Site.AccountId` — is inside the guard rather than beside it. What the traversal
   still cannot see is stated in `TenantScopeCensus`: an OPTIONAL foreign key is not followed (a row
   that may exist with no owner is not an owner's row), a tenant column spelled as anything else on
   an entity with no relationship to one is invisible, and so is an entity related only by a join
   some handler writes and the model does not know about. An entity
   that must NOT be filtered is named in that test's exemption list with the reason it is safe, and
   an exemption for an entity that no longer exists fails too. `IgnoreQueryFilters` is a banned
   symbol in `backend/src`, so each deliberate bypass carries its reason on the line. The answer for
   a resource another account owns is **404, never 403** (`ErrorType.NotFound`) — a 403 confirms the
   row exists — and each tenant module still carries its own IDOR test proving the endpoint answers
   that way.
7. **Configuration is documented, secrets are not committed:** every variable the product reads has an entry in an `.env.example` (repository root for development, `docker/.env.example` for the dev stack, `installer/panel.env.example` for what the installer generates on a server). The example files carry names, comments and safe placeholders — never real values. `.env` itself is git-ignored.
8. **Secrets:** never in logs, error messages, URLs, or git. This includes anything that *acts* as a secret — a one-time setup token is permission to become the administrator, so it goes to the operator's terminal and never to a log file that outlives the install. Customer-facing errors carry no paths, versions, or tool output (role-aware error mapping). New config values with secrets go to `panel.env` (root:maran 0640 — `maran` is the unprivileged system user and group the API runs as, named in installer/install.sh), not appsettings.
9. **Crypto:** Argon2id for passwords (a mailbox password is stored in the strongest scheme the host's Dovecot supports, chosen once by the distro adapter as `MailPasswordScheme`; the panel's own logins are always Argon2id); Ed25519 for licences (`Ed25519LicenceSignatureVerifier`); ECDSA P-384 with SHA-384 for release manifests and artifacts (`installer/keys/release-signing.pub`, `installer/lib/50-artifacts.sh`), for module packages (`installer/keys/module-signing.pub`, `IpmSignatureVerifier`) and for the marketplace's catalogue, update, key-list and download-grant answers (`installer/keys/marketplace-metadata.pub`, `CatalogueSignatureChecker`) — four keys, two schemes (licence Ed25519; release, module-signing and marketplace-metadata P-384), and a reviewer checks the one the code under review actually uses. The two P-384 verifiers share one implementation, `SharedKernel/Utilities/Signatures/EcdsaP384Signature`. The module-signing key is offline and signs packages only; the marketplace-metadata key is an online service key and signs answers only, so a stolen metadata key can misdescribe the catalogue but cannot make a package acceptable. The owner supplies the two `.pub` files; the repository commits none; XChaCha20-Poly1305 (the agent's `chacha20poly1305`) for the encryption of backups at rest, mandatory for a remote destination, under a key the panel holds and that can be recovered only from the panel recovery archive; TLS everywhere external; no home-grown crypto, no MD5/SHA1 for anything security-relevant.
10. **Surface:** no new listening ports, no new daemons, no new outbound calls beyond those named here beyond those named here. Anything of the kind requires a spec change first, not a PR. **Eleven documented exceptions.** The first two are the root `maran` CLI fetching a signed release manifest and its artifacts over HTTPS, never the API and never the agent, sending no identifier: (1) when an operator runs `maran update` or `maran update --check`; its call-free alternative is `--offline-tarball` (**owner decision: approved, decision list item 2, option a, applied 2026-11-12**); (2) the security-patch timer: `maran-update-security.timer` starts `maran-update-security.service` once a day (midnight plus up to four hours of random delay), which runs `maran update --security-only --scheduled`. It applies a release only when the signed manifest marks it `security` and its major version is the installed one. The timer is OFF by default: an install, online or offline, only installs the units and tells the operator on the terminal; `maran update-schedule enable` opts in, `maran update-schedule disable` switches it off, and neither the installer nor `maran update` changes the choice. Its call-free alternative is to disable it and use `--offline-tarball`. (3) The third is the ROOT AGENT's outbound SSH to an operator-registered migration source (issue #197, `ops::transfer`; threat note `docs/superpowers/notes/2026-11-07-server-migration-threat-note.md`), the agent's first network client. It happens only on an administrator's act (registering a source, scanning its host key, testing the connection, reading its inventory), only to the one host and port the administrator registered, and only after the administrator confirmed the host key's fingerprint as a step of its own; the key is pinned with `StrictHostKeyChecking=yes` against a known_hosts file the agent writes itself. The address is resolved once and judged on the RESOLVED address (loopback, link-local, unspecified, multicast and the host's own addresses are refused; a private range is allowed on purpose, so an administrator can make the root agent attempt an SSH handshake to any internal host, which is why the connection is audited and bounded to one registered host). What runs on the source is a closed enum of constant read-only commands with validated holes, and nothing is written there. The credential is a per-source ed25519 key, stored encrypted by the panel and handed to the agent per call; there is no root-password flow. It listens on nothing and has no automatic trigger: its call-free alternative is not registering a source. **Owner approval: applied from the recommended option, owner decisions D6, D14 and D15 of the migration section pending confirmation, and so are the threat note's open questions 1, 3 and 4** (a root agent as an SSH client at all, a registered source on a private address, the stated limit that the key cannot be read-only); the applied decisions are listed in the threat note under "Phase 1 as built". This item is amended again when the owner answers, and nothing here claims that he has. (4) The fourth is the MARKETPLACE: the panel process (`maran-api`, as the unprivileged system user) may contact the single host `api-marketplace-maran.innovayse.com` over HTTPS (configurable with `Marketplace__BaseUrl`; the configured host is the whole allow-list), and only (a) when an administrator opens or refreshes the Marketplace screen, searches it, opens a module, checks for updates, or asks to install or update a module — never from a timer, a start-up step, a background job, or a request made by anyone but an administrator — and (b) when an administrator has switched the marketplace on (off by default; a database row with no environment path; audited). What it sends is limited to: the panel version, the release channel, the interface language, the administrator's search text and page cursor, the id and version of the module in question, the lease credential — to the catalogue, module-details and update requests only so the licence's entitlements can be shown, and to the download-grant request, and never to the host's key list or to the package download — and, on the update check only, the id, version and package digest of the installed modules asked about. It sends no host name, account, site, user or customer data; the connection's source address is visible to the host, as with any HTTPS request. It refuses a redirect to any other host or port, verifies every catalogue, module, update, key-list and grant answer against the pinned marketplace metadata key before using it (item 9), and verifies every package against the module-signing key before anything is loaded. Its failure leaves installed modules running exactly as they were. Its call-free alternative is to leave the marketplace switched off. Documented for operators in `docs/operations/marketplace.md`; threat note `docs/superpowers/notes/2026-11-07-marketplace-loader-threat-note.md`. **Owner decision: approved (decision list items 46 and 47, option a), 2026-11-09.** (5) The fifth is the LICENCE LEASE RENEWAL: the panel process (`maran-api`, as the unprivileged system user) contacts the single host `api-marketplace-maran.innovayse.com` over HTTPS (configurable with `Licensing__LeaseServiceBaseUrl`; the configured host is the whole allow-list), on a timer, by design: a background worker of the Licensing module, registered by the Host, makes one `POST /api/v1/lease` about once a day (a first attempt a few minutes after start, then about 22 to 24 hours after a stored lease, about 6 to 7 hours after a failure, with random jitter), and only when a licence that is not an offline licence is installed and verifies and its stored lease is older than 20 hours or missing. The same pass also runs once, at once, when an administrator installs or replaces a licence (issue #537): the install asks for it after the install lock is released, it is the identical pass with the identical request, journal entry and alert, and the schedule's next wait follows its outcome; it is an administrator's act and never a timer, a start-up step or a request made by anyone else. What it sends is the licence id in a JSON body, and nothing else: no panel version, no host name, no machine id, no account, site, user or customer data, no `Authorization` header and no cookie; the connection's source address is visible to the host, as with any HTTPS request. It follows no redirect, reads at most 16 KiB of answer, and writes the answer to the lease file only after it parses, verifies against the pinned lease key (Ed25519, item 9), names this licence and this server, is no older than a day and no newer than the clock allows, and ends later than the lease already stored; any other answer changes nothing, and the stored lease keeps covering the paid modules for the rest of its life. Each stored lease and each failure is written to the audit journal as the panel, and repeated failure raises an operator alert through the existing notifications. Its call-free alternative is an offline licence, which needs no lease and is never renewed over the network. Documented for operators in `docs/operations/licensing.md`; the contract is `docs/marketplace/api-v1.md` ("Lease renewal"); threat note `docs/superpowers/notes/2026-11-07-licensing-lease-threat-note.md` (fourth amendment). **Owner decision: approved from the recommended option (decision list item 46, option a: the panel API makes the call through the named outbound pipeline, licence id only), applied 2026-11-09; the second review of this surface is OUTSTANDING (#331).** (6) The sixth is the ALERT WEBHOOK: the panel API (never the agent, never the CLI) posts one JSON alert (source, severity, short text; no credential, path or customer data) to the URL an administrator saved in the alert settings, once per alert event, through a named `WebhookPipeline` with its own `HttpClient` (not built yet; the pipeline lands with the webhook), so that the call cannot be made ungoverned. The destination is the administrator's choice: `https` only, loopback, link-local and cloud-metadata addresses are refused on the address actually connected to and not on the host name, redirects are not followed, and a failed delivery is not retried in v1 but is a visible state on the dashboard. The body is signed with HMAC-SHA256 over the timestamp and the body (`X-Maran-Timestamp`, `X-Maran-Signature`; the key is shown once). With no URL saved nothing is sent; its call-free alternative is e-mail and the notification feed. **Owner decision: approved (decision list item 44, option a, with this guard), applied 2026-11-12.** (7) The seventh is REMOTE BACKUP UPLOAD to an S3-compatible bucket the operator configured, over `https` only and only after the operator (`maran panel-backup`, the root CLI) or an administrator (account backups, the agent's object-store seam) configured the destination; nothing is uploaded to a default or Innovayse-owned location. What leaves the server is ciphertext only (item 9; the key never leaves the server), with no panel, licence or host identifier; the credentials are held encrypted at rest and never logged; the panel never deletes a remote copy. Its call-free alternative is the local destination. **Owner decision: approved (decision list items 45 and 14, option a and b), applied 2026-11-12.** (8) The eighth is MAIL: Postfix and Dovecot (with Rspamd), the distribution's own units masked and Maran units installed disabled (rules/architecture.md System boundaries), enabled only when an administrator turns mail on, listen on SMTP 25/465/587 and IMAP 143/993 (POP3 110/995 only behind a separate switch) and make outbound SMTP to other mail servers, which is the function itself. Submission needs TLS and authentication, relaying is refused for unauthenticated clients, the webmail API reaches Dovecot and Postfix over unix sockets and never a TCP port, and the panel reports the ports without opening them. While mail is off nothing listens. **Owner decision: approved (decision list item 48, option a), applied 2026-11-12.** (9) The ninth is REMOTE DATABASE ACCESS on tcp/3306: only for plans that carry the remote-access feature (off until sold), only to single addresses a customer added for one of their own database logins, one firewall rule per address, never a range or the open internet; the login is bound to that address in MariaDB too (`MAX_USER_CONNECTIONS` bounded; not built yet, issue #156), and while no address exists the database listens on no network interface. TLS is not required in v1, which the interface says in plain words. It is a sensitive change: its threat note comes first and its second review is OUTSTANDING (#331). **Owner decision: approved (decision list item 49, option a), applied 2026-11-12.** (10) The tenth is the FLEET NODE CHANNEL: on a managed node (an agent-only server, rules/architecture.md) the agent listens on tcp/8444 over mutual TLS, only after enrolment and only for the panel's address (`--allow-from`; `--allow-any` is refused without an explicit warning flag), and an enrolment endpoint accepts one single-use token and nothing else, rate limited and with a failure lockout; the primary panel makes outbound connections to enrolled nodes only, at addresses an administrator approved by typing the node certificate's fingerprint. Trust is pinning, with no certificate authority and no phone-home; nothing is sent to Innovayse. A compromise of the primary panel is a compromise of every enrolled node, and the threat note (`docs/superpowers/notes/2026-11-07-fleet-threat-note.md`) says so; its second review is OUTSTANDING (#331). **Owner decision: approved (decision list item 50, option a), applied 2026-11-12.** (11) The eleventh is the DNS SERVICE: an authoritative DNS daemon (BIND 9), run through a Maran unit installed disabled, the distribution's own unit masked (rules/architecture.md System boundaries), and enabled only when an administrator turns DNS on, then listening on tcp/53 and udp/53 and serving the zones the panel renders; its rndc control channel is loopback only and is not a listening surface for this item. Zone transfer is outbound-served only (to named secondaries); the panel never pulls a zone from another server. The firewall rule is added by enabling DNS and removed by disabling it. Threat note `docs/superpowers/notes/2026-11-07-dns-module-threat-note.md`; its second review is OUTSTANDING (#331). **Owner decision: approved (decision list item 51, option a), applied 2026-11-12.** The OIDC discovery fetch of the marketplace service (decision list item M2) is that service's own outbound call and changes nothing on the panel side. Destinations an operator configures for a stated purpose (for example the ACME directory for certificates) are the operator's choice and send only what that purpose needs; they are not Innovayse destinations and not covered by this list — this sentence is an observation, because the item never named ACME, and is flagged for the owner to confirm or move. The panel's own outgoing mail (the Notifications SMTP) is not an eleventh exception: it goes to the SMTP server the administrator configured, like the ACME directory, and is covered by the sentence above. Any other automatic check needs its own spec change.
11. **Dependencies:** additions need a one-line justification in the PR; `cargo audit`/NuGet/`npm audit` clean; pinned versions.
12. **Agent:** new rpc = closed typed command, idempotent, re-validated, audited; customer file ops under account UID. Anything resembling "run this for me" is rejected on sight.
13. **Module reach into the agent is declared and enforced.** `Maran.Agent.Client` is one door to
    the only root process on the server, shared by every module in the panel process, so a module
    that has no business touching the firewall could nevertheless resolve `IAgentFirewallClient` and
    open a port. Every module's `Manifest` therefore lists the `AgentCapability` values it needs, an
    administrator sees that list before installing, and `AgentCapabilityGuard` refuses to compose a
    module whose declared dependencies reach past it — at startup, and again in CI. A new agent
    service must add a value to `AgentCapability` or the guard throws rather than treating it as the
    one part of the agent nobody has to declare. **Stated limit:** a module that takes
    `IServiceProvider` and asks for a client at runtime declares nothing in its metadata and is not
    caught; service location is already a review reject, and closing it properly means not
    registering the clients in the shared container at all.
    **Packaged modules.** The same guard
    runs at composition for a module that arrives as a package (`PackagedModuleComposer` calls
    `AgentCapabilityGuard.Verify` on the candidate's types): a package whose dependencies reach an
    agent client its manifest did not declare, or whose manifest or signature fails, is refused, left out and journalled, never partly loaded, and the panel starts without it
    instead of failing. The stated limit applies to packages in full: a packaged module's declared
    capabilities are what its constructors take, so one that asks an `IServiceProvider` for a client
    at run time declares nothing and is not caught, and the check reads the module's own types, not
    what it does. Whether the loader gives a package a narrower container than the panel's is the
    closed loader's and is not claimed here.
14. **A packaged module's screen is untrusted code in an opaque origin, and the server holds the
    line.** The shell shows it only in `UiSandboxFrame` (`sandbox="allow-scripts"`, never
    `allow-same-origin`), served from `/module-frames/{id}/{version}/` with a CSP that gives the
    frame no network (`connect-src 'none'`) and no inline script, behind an nginx location with its own
    complete header set (the rest of the panel keeps `X-Frame-Options DENY` and `frame-ancestors
    'none'`). The frame document is generated by the panel; only a pinned classic script and
    extension-allow-listed static assets come from the package, an `.html` file never. The frame
    reaches the API only through the shell's message bridge, and the shell marks each relayed request
    `X-Maran-Frame: <moduleId>`; `ModuleFrameScopeMiddleware` then refuses (403
    `ModuleFrameOutOfScope`) any endpoint that module does not own, and any endpoint no module owns.
    The shell's own path check is advice. No token, cookie, CSRF value or user object is ever sent into
    the frame. **Stated limits:** the bridge handshake's behaviour in Firefox and WebKit is not
    measured here (Chromium only); a module's BACKEND is trusted code in the panel process as the
    unprivileged user, so the frame boundary protects the administrator's session from a module's
    screen, not the panel from a module's assembly.

## Sensitive change escalation

Changes to auth, session/token handling, the agent's privs module, license verification, or the installer's privileged steps require a second reviewer and an explicit threat note in the PR description: what could an attacker do with this surface, and why is it safe now.

**When no second reviewer can be obtained, the change is NOT compliant — and this rule says so
rather than pretending otherwise.** Most work in this repository is done by agent sessions, which
cannot dispatch a reviewer; several privileged changes have therefore landed in the working tree
with a written threat note and the reviewer requirement recorded as OUTSTANDING. That is a real
gap, not an alternative path, and the rule is not weakened to describe it as one: the second
reviewer exists because the author of a privileged change is the person least able to see what they
assumed, and a threat note written by that same author closes nothing. What it does buy is that the
reviewer, when they arrive, reads an argument instead of a diff.

So the deferral is permitted only in this exact shape, and it is a debt with a name:

- The threat note is written **first**, before the change, and lands in `docs/superpowers/notes/`
  as a file, not as prose in a report that only one session ever reads. Written after the fact it
  is a justification validating a choice already made, which rules/architecture.md names as the
  mechanism that stops the next reader looking.
- The note states the requirement as **OUTSTANDING**, names what a reviewer must check, and names
  what the author could not verify.
- The change **may land on a branch; it MUST NOT merge to `main`.** `main` is protected and the
  second reviewer is a merge gate (rules/git.md "Pull requests"), so an outstanding review means an
  unmergeable branch — which is the honest state and the one the owner can see.
- The owner is told at hand-off which privileged surfaces are carrying an outstanding review.

A note recording the debt is the minimum, never the discharge of it.

### The one recorded exception: beta pre-releases

The owner may decide, in writing and per release, that a **pre-release** (a `-beta.N` tag published
as a GitHub pre-release) reaches `main` while second reviews are still OUTSTANDING. It is an owner
decision, never an author's, and it is bounded:

- It applies to the one release it names. The next release needs its own decision.
- The release notes and that release's CHANGELOG section say, in plain words, that the second
  review of the privileged changes is outstanding, so nobody running the release mistakes it for
  reviewed.
- The threat notes stay OUTSTANDING. Shipping a beta discharges no review.
- A stable release is never covered: the second reviewer remains a merge gate for it.

Recorded uses: **1.0.0-beta.4**, approved by the owner on 2026-11-01.

`SECURITY.md` at repo root carries the report contact and the promise: acknowledge in 48h, fix-or-mitigation target 14 days for critical. Vulnerabilities are never discussed in public issues before a fix ships.
