# Threat note — release bundle build, signing and verification

Required by `rules/security.md` ("Sensitive change escalation"). Covers the new
`scripts/lib/release-bundle.sh` (wired as `maran release build|sign|verify|selftest`),
which produces the exact artefact `installer/lib/50-artifacts.sh` verifies before an
install unpacks anything: a manifest of per-component sha256 checksums, an Ed25519
signature over that manifest, and a single tarball an operator moves to a server or an
online release channel serves. **This change needs a second reviewer. That review is
OUTSTANDING** — written by the same session that wrote the change, which
`rules/security.md` names explicitly as not a substitute for a second reviewer: the
author is the person least able to see what they assumed. This note is written FIRST,
before the builder script, per the rule.

## What this surface is

`installer/lib/50-artifacts.sh` is the installer's only trust boundary against a
compromised download mirror or a MITM on the download path (its own header comment,
`installer/lib/50-artifacts.sh:1-6`). It refuses to unpack anything until:

1. `manifest.json`'s Ed25519 signature verifies against a public key baked into the
   installer package at `${SCRIPT_DIR}/keys/release-signing.pub`
   (`installer/lib/50-artifacts.sh:28`, checked at
   `installer/lib/50-artifacts.sh:70-88`).
2. Each of `api`, `agent`, `frontend`'s sha256 (read out of that now-trusted manifest)
   matches the downloaded/unpacked bytes (`installer/lib/50-artifacts.sh:123-150`,
   `179-206`).

This change adds the other half: something that produces a manifest, signs it, and
packages it the way step 50 and `use_offline_tarball` read it. It runs on a developer
or CI machine, never on the installed server, and it never ships a private key —
signing takes a key path from an environment variable or `--key` argument pointing
**outside this repository**, and refuses when it is absent
(`scripts/lib/release-bundle.sh`, `sign()`/`require_signing_key()`).

## Attacker model and what the signature protects

- **An attacker who can replace the *bundle* on a mirror, but not the public key
  shipped in the installer package or the private key**: fully defeated. Any byte
  changed in a signed component invalidates its checksum against the untouched,
  signed manifest; any change to the manifest invalidates its signature. This is the
  case `50-artifacts.sh` was written for and the case this change's `verify`/`selftest`
  subcommands exercise directly (see Verification below).
- **An attacker who can replace the *public key* file shipped alongside the installer
  (`installer/keys/release-signing.pub`) as well as the bundle**: fully defeated
  against the check, same as `50-artifacts.sh`'s own header already says — "an
  attacker who can serve the installer AND a fake manifest would otherwise control
  both halves of the trust check" (`installer/lib/50-artifacts.sh:24-25`). Whoever
  distributes the installer package is the actual trust root; this change does not
  alter that, it only produces the artefact the existing check consumes. Nothing here
  distributes the installer package itself.
- **An attacker who compromises the *signing private key***: fully defeated against —
  they can sign anything and every install will accept it. This is why the key must
  never enter the repository, never be generated by this tooling, and never be
  printed; `release-bundle.sh sign` only ever reads a path the operator supplies and
  calls `openssl pkeyutl -sign`, the same primitive `50-artifacts.sh` verifies with,
  never writing the key's bytes anywhere itself.
- **What the signature does NOT protect against**: a legitimate release built from
  malicious or defective source. Signing attests "this manifest was produced by
  whoever holds the key", not "this code is correct" — the same limit every code-
  signing scheme has, and one this change does not attempt to close.
- **The build host itself**: this tooling assumes the machine running `maran release
  build`/`sign` is not already compromised. A compromised build host could sign
  anything the operator's key can sign; that is a build-environment integrity
  problem, out of scope for a bundling script and unchanged by this work.

## What a reviewer must check

- That `sign()` truly never reads a key from inside the repository by default (no
  fallback path under `installer/keys/` or elsewhere in the tree), and that the
  `installer/keys/*.key` / `*-private*` ignore rule actually matches whatever the
  operator would name a private key, without also matching the public key that is
  meant to ship.
- That `verify()` uses the *exact* `openssl pkeyutl -verify -rawin` invocation
  `50-artifacts.sh:78-82` uses (not a different digest mode, not a different verifier
  such as `openssl dgst`) — a verify step that passes on a scheme the installer
  doesn't use would be exactly the "decoration" `rules/testing.md` warns against.
- That the manifest field shape this script writes is read correctly by
  `installer/lib/50-artifacts.sh`'s `manifest_field` awk reader
  (`installer/lib/50-artifacts.sh:91-104`), not just by `jq` — the installer
  deliberately avoids `jq`, and a manifest that jq accepts but the awk reader misparses
  would pass this script's own verify and still fail on a real install.
- Whether the component tar layout (files at the tarball root, not nested in a
  `bin/` or version subdirectory) matches what `installer/lib/70-services.sh`'s
  `ExecStart=/usr/local/maran/api/Maran.Host` and
  `ExecStart=/usr/local/maran/agent/maran-agent
  (`installer/systemd/maran-api.service:24`, `installer/systemd/maran-agent.service:70`)
  and the nginx `root /usr/local/maran/frontend;` (`installer/nginx/maran.conf:129`)
  actually expect — verified here by unpacking a built bundle and checking the paths
  land where those units already point, not by re-deriving the paths from memory.

## What could not be verified in this environment

- **No real release build was produced or signed with a production key.** This
  session has no access to whatever private key Innovayse's release-signing
  infrastructure holds, nor should it — the note above states plainly that deciding
  where that key lives is the owner's decision, not this session's. Verification here
  used a throwaway Ed25519 keypair generated only for the `selftest` subcommand's own
  use, deleted after the demonstration, never committed, and never treated as a real
  release key.
- Whether `backend`, `agent` and `frontend` build cleanly enough on this machine right
  now to produce real publishable artefacts was checked at build time — the selftest
  verified against a **synthetic** bundle (three placeholder component archives, not real
  binaries), signed with a throwaway key generated and discarded in the same run, not
  against a real release build — since another lane owns quota work under `agent/crates/ops/` and
  `backend/src/Maran.Modules/{Monitoring,Accounts}` concurrently and the tree write
  lock may refuse a build lane at any point; a refusal is `DID NOT RUN`, not a defect.
