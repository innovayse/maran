   No new surface beyond the validated-drafts argument below.

## Owner decisions this change assumes (recommended options, approved for implementation)

- DT1 a closed variable set `{apex} {ipv4} {ipv6} {ns1} {ns2} {hostmaster}`, no expression language.
- DT2 template records carry origin `Template`, are editable by the zone's owner, and become `Customer` when
  edited. `System`, `Mail` and `AcmeChallenge` records stay read-only.
- DT3 templates are edited by administrators only. DT4 a default template, "web", seeds zones created from a site.
- D4 the panel generates ECDSA P-256 keys and keeps them encrypted at rest (truth stays in PostgreSQL, a rebuilt
  host is re-keyed from the database). DS1 one combined signing key, no automatic rollover in v1.
- DS2 a withdrawal takes effect after a 48 hour minimum, enforced by the server, for administrators too.
- DS3 DNSSEC is hidden on a host whose daemon cannot sign, decided by observation. DS4 the zone's owner and
  administrators may enable it.

## S5: what an attacker could do with templates, and why it is safe now

- **A template is a second author of record data, so it gets no second validation path.** The administrator's
  template stores typed fields (name, type, ttl, value, priority, weight, port, flags, tag) and the closed
  tokens. Expansion is a pure function; every draft it produces is then passed through the SAME
  `RecordShapePolicy` and `ZoneRecordRules` a customer's own record passes, at template save (against a sample
  context) and again at zone creation (against the real context). The agent re-validates each value regardless
  (`validation/dns/*`). A template therefore cannot place a newline, quote, backslash, `$INCLUDE` or an
  out-of-zone name into a zone file: the same typed fields refuse them. Tokens are substituted as text into
  fields whose grammar is then checked; there is no recursive or nested expansion, no expression, no
  filesystem or environment reference. An unknown or unbalanced token is refused when the template is saved.
- **A variable whose setting is empty skips the record.** No IPv6 address in the settings means the AAAA record
  is not created; the result lists what was skipped. The panel never invents an address.
- **Who can read or write templates.** Template management is administrator-only (`AdminOnly`). A customer
  receives id, name and the default flag of the templates (`.../templates/choices`) and never their records;
  a test proves a customer token gets nothing from the administrator endpoints. Templates are server-wide
  administrator data with no account id, so they carry an explicit, reasoned entry in the tenant-scope
  census exemption list (a template is not a customer's row), and the census still fails for any other
  unfiltered entity.
- **Origin `Template` is editable.** A customer may change or delete a record a template created; the edit
  turns it into `Customer`. This widens what the customer can edit by exactly the records an administrator
  gave them and nothing else: the rule lives in one policy (`RecordOriginPolicy`), `System`, `Mail` and
  `AcmeChallenge` remain refused, and the mutation "make ChangeRecord accept `System`" is covered by a named test.
- **Resource exhaustion.** A template's record count is bounded by the per-zone record cap at save, and the
  cap is enforced again when a zone is created from it, so a template cannot be used to exceed a plan.

## S6: DNSSEC

### 1. Key custody (secrets, item 8)

- The panel generates one ECDSA P-256 key per zone with the platform's `ECDsa` (no hand-written crypto), stores
  the public part in the clear and the private scalar encrypted through the panel's `IEncryptionService`
  converter. The private scalar exists in plaintext only in memory, in the one call that builds the agent request,
  and in the agent's memory and the key file described below.
- It is never part of any DTO, log line, audit entry, task failure row, error body or the OpenAPI document.
  Tests plant a recognisable key value and search all of those places, with a positive control proving the
  search can see a planted value; a mutation that logs the key must fail a named test.
- On the agent the private part is a `SecretString` whose `Debug` and `Display` redact; the validated key type
  has no `Display` of the private half; errors carry the field that failed and never a byte of the key.
- **Residual**: the key file on the host is readable by the daemon's group (it must be, the daemon signs with
  it). A compromise of the daemon yields the signing key of every signed zone. That is inherent to online
  signing by the daemon; the mitigation is that the daemon is the unprivileged, confined, rate-limited one and
  that the key is re-generated by withdrawing and enabling (outside the 48 hour window only after the DS at the
  registrar is replaced). Stated, not removed.

### 2. Signing travels inside `PutZone` (no new rpc, no second writer)

The agent is stateless and the database is the truth. After a host rebuild or a reconciler pass the keys must be
reinstalled from the database, which `PutZone` already does for records. A separate `SetZoneSigning` rpc would
make two writers of one fact. The request carries `mode` (unsigned, signed, withdrawing) and, for the last two,
the key. The reconciler sends the stored signing config with every zone; without it a rebuilt host would serve an
UNSIGNED zone while the registrar still holds the DS record, which fails validation for every validating
resolver (an outage). The reconciler test is the single most important integration test of this change.

### 3. The agent writes key files as root next to a daemon that writes beside them

- Key files `K<zone>.+013+<tag>.key` and `.private` are written by the root agent through `safe_write`
  (temp file in the same directory, fsync, atomic rename) as `root:<daemon group>` mode `0640`, from validated
  inputs only. The file name is built from the validated zone name and the RECOMPUTED key tag, never from a
  caller-supplied tag. The request's key tag must equal the recomputed RFC 4034 appendix B tag or it is refused.
- Inline signing makes the daemon write `<zone file>.signed` and a journal beside the zone file, and the daemon
  writes `.state` files next to the keys. So two directories, `<state>/signed-zones` and `<state>/keys`, are
  `root:<daemon group>` `0770`, while the plain zone directory stays `0750` and read-only to the daemon. Signed
  zones' files live in the signed directory so the unsigned hardening is unchanged for every other zone.
- **Root writing into a directory the daemon can write.** The risk is a planted symlink or swapped entry. The
  agent only creates files through the rename-onto-name protocol (a rename replaces a symlink, it never follows
  it), never opens an existing name for writing, never `chmod`/`chown`s by path, and names files from validated
  types. A compromised daemon can still delete or replace its own zone and key files; it can already tamper with
  what it serves, so this adds persistence of that ability and no escalation to root. A reviewer must check that
  no agent code path in these directories follows a name it did not just create.
- SELinux: both directories inherit `named_cache_t` from the state directory rule, which the daemon may write;
  the plain zone directory keeps `named_zone_t`. AppArmor: the installer's local override gains the two paths.
  UNOBSERVED HERE: that either confinement permits it on a real host (polygon suite `dns_on_a_real_host`).

### 4. The outage guard (the one irreversible customer mistake)

Disabling DNSSEC while the DS record is still published at the registrar makes the zone fail validation for every
validating resolver. The panel cannot see the registrar. So:
- Withdrawal is a state, not an action: `Signing -> Withdrawing` switches the daemon to the built-in `insecure`
  policy WITH THE SAME KEY (resolvers keep a consistent answer while the DS is removed);
  `Withdrawing -> Off` deletes the key and is refused by the SERVER before 48 hours after the withdrawal began
  (the injected clock is the only time source) and unless the caller states the DS was removed. The SPA cannot
  bypass the wait; the warning is mandatory text in the confirmation dialogs. Deleting a signed zone shows the
  same warning (it is allowed because account deletion cascades zones).
- UNOBSERVED HERE: that a DS record is, in fact, gone at a registrar. The panel states a duty, it does not verify one.

### 5. The daemon's capability is observed, not assumed

`dnssec-policy` exists from BIND 9.16, and the release 8 branch of the RHEL family is unverified here. A build
that lacks it refuses the whole configuration, so the policy cannot be rendered unconditionally. EnableDns asks
the daemon's own checker (`named-checkconf`) about a probe configuration stating a policy and renders the policy
only when it was accepted; the answer is reported (`dnssec_supported`) and the panel hides DNSSEC when it is
false. A probe that could not run reports false (hidden), never true.

### 6. Amplification

A signed zone's answers are larger (DNSKEY, RRSIG). Response rate limiting, minimal responses and the 1232 byte
EDNS size stay in force; none of them is relaxed. UNOBSERVED HERE: the measured amplification factor of signed
versus unsigned answers. It must be measured on a real host and written here before the second review closes.

### 7. Configuration injection

The zone statement (`rndc addzone` / `modzone`) is rendered from a template, with the zone file path built from
the validated zone file name and the two directory facts; no caller string reaches it. The key file body is
rendered from the validated key type (base64 alphabet, fixed lengths, fixed algorithm). `rndc` is run by argv.

## What a reviewer must check

1. Template expansion output re-enters `RecordShapePolicy`/`ZoneRecordRules`; delete that call and a named test
   (planted template record with a newline in its text) fails; the control (a valid template) passes.
2. `ChangeRecord`/`RemoveRecord` still refuse `System`, `Mail`, `AcmeChallenge`; accept `Template` and `Customer`.
3. A customer token receives 404/403-equivalent from every administrator template endpoint and never sees template records.
4. The private key appears in no DTO, log, audit row, task failure or OpenAPI schema (planted value + positive control).
5. The agent refuses: a key of the wrong length, algorithm other than 13, flags other than 257, a mismatching key tag,
   non-base64 and control characters (one named test each), and an UNSIGNED request that carries a key.
6. `finish-withdrawal` before 48 hours is refused for an administrator as well; after 48 hours with the confirmation it
   succeeds (injected clock); without the confirmation it is refused.
7. The reconciler re-sends the stored signing config (a rebuilt host test).
8. No agent code in `<state>/signed-zones` or `<state>/keys` opens an existing name for writing or follows one.
9. The rendered `named.conf` states the policy only when the probe said the daemon accepts one (both goldens).
