# The API description

The panel's HTTP API is described by one OpenAPI 3 document, generated from the controllers of the
tree it is built from. It exists for the people who write clients against the API (the provisioning
integrations first), and so that a change that would break such a client is caught on the branch that
makes it and not by the client.

The provisioning API (`api/v1/reseller-api/`) has a reference page, [provisioning.md](provisioning.md), and
a machine-readable contract of the sequence a billing provider relies on,
[billing-contract/lifecycle.json](billing-contract/lifecycle.json) (how to replay it:
[billing-contract/README.md](billing-contract/README.md)). An integration test replays that file against
the real panel in CI, so a route, status, required field or type that the file relies on cannot change
unnoticed.

## What the document is

- **Generated by the panel itself.** `Maran.Host --cli openapi <path>` writes the document and exits.
  It starts no listener, opens no database connection and calls no agent. The panel serves the
  document nowhere: a runtime endpoint for it would be a new surface (rules/security.md item 10).
- **Held in `docs/api/openapi-baseline.json`.** The committed baseline is the contract integrators are
  promised. The generated document is compared against it by `scripts/lib/openapi-diff.mjs`.
- **Attached to every release** as `openapi.json`, generated from the tagged tree by
  `maran release openapi`. It is signed with the release key (`openapi.json.sig`, attached beside it)
  and checksummed in `SHA256SUMS` with the other assets. See `docs/operations/release-process.md`.

## Running the check

Run these as an unprivileged user (the panel refuses to run as root):

```
source scripts/dev
maran openapi selftest    # the detector's planted controls; needs node only
maran openapi             # generate, compare with the baseline, print a verdict
maran openapi --accept    # record the generated document as the new baseline
```

`maran openapi` prints exactly one of three verdict lines, and CI passes on the printed line:

| Line | Status | Meaning |
|---|---|---|
| `OPENAPI VERDICT: OK` | 0 | a document was generated and holds no breaking change |
| `OPENAPI VERDICT: FAILED` | 1 | a breaking change, a missing baseline, a build or generation failure, or a document that describes no operation |
| `OPENAPI VERDICT: DID NOT RUN` | 2 | node or the .NET SDK is missing, or the command was run as root: nothing was generated and no verdict about the API exists |

## What counts as breaking

The comparison asks whether a client written against the baseline would still work. It is
directional: a response is something the server produces, so a client breaks when something it read
goes away or changes shape; a request is something the client produces, so a client breaks when the
server starts demanding something the client never sent.

Breaking (fails the check): a removed path or operation, a removed response status, a removed or
retyped response property, a response property that became nullable or optional, a removed enum value, a request property that became non-nullable or gained an enum, a removed media type, a new required request
parameter or property, a parameter or property that became required, a removed or retyped request
parameter or property, a new or newly required request body, and a security requirement or scope
added to an operation.

Additive (passes, and is reported so the baseline can be brought up to date): a new path, operation,
response status, response property, enum value, media type, optional request parameter or property,
and a security requirement removed or an alternative added.

The full list of kinds is the `KINDS` table in `scripts/lib/openapi-diff.mjs`; the detector's selftest
requires that every kind is produced by at least one planted pair.

## Recording a baseline, and an intended breaking change

- **Additive changes** pass without recording anything. Run `maran openapi --accept` when you want
  the baseline to describe them, and commit the file.
- **An intended breaking change** is recorded with `maran openapi --accept` **in its own commit**,
  containing only `docs/api/openapi-baseline.json`, whose message names the break and why it is
  accepted. The diff of that one file is what a reviewer reads. A breaking change mixed into a larger
  commit is a review reject. `--accept` refuses a document that describes no operation, and is never
  run in CI: a check that refreshes its own baseline enforces nothing.
- Per rules/architecture.md the Provisioning API only gains endpoints and fields inside a major
  version; a breaking change here is a decision for a new major version, not a routine edit.

## Blind spots

The check prints these on every verdict. A green line is a statement about the description, not the
running server.

- Runtime behaviour: only what the document describes is compared. A validator that rejects a value
  the schema accepts is invisible.
- Authentication the document does not describe: a scheme or policy absent from it cannot be seen.
- Endpoints the generator does not list: non-controller (minimal) endpoints appear only if it lists
  them.
- Validation keywords (length, range, pattern, `uniqueItems`, `additionalProperties`) and the definitions of
  security schemes are not compared.
- Operations are identified by path template plus method, so a renamed route parameter is reported as
  one removed and one added path. `oneOf`/`anyOf` are compared by position; response headers, links,
  callbacks, `not`, discriminator mappings and `x-` extensions are not compared.
- The release document is generated from the tagged tree, not read from a deployed panel.
